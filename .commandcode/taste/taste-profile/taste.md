# Taste Profile
- Expects skeptical, evidence-based verification: "assume a capability is broken until proven otherwise." Don't treat reading code as proof — actively trace execution paths and run/create tests to confirm behavior. Confidence: 0.75
- After implementation (especially security-critical: identity, account linking, money), explicitly asks for the implementation to be verified deeply — expects a self-adversarial review pass that critically reviews the agent's own diff, writes tests that try to break the new paths, and surfaces bugs in the agent's own prior work. Confidence: 0.55
- Rejects implication-by-existence: a tool merely existing, being registered, having a schema, or having unit tests is NOT evidence it works. Only the full end-to-end path (intent → correct tool → authenticated context → real execution → valid result → truthful response) counts as operational. Confidence: 0.7
- Insists on distinguishing MOCK VERIFIED from REAL INTEGRATION VERIFIED, and forbids treating mocks as proof of production functionality. Confidence: 0.7
- Do not fabricate test results, and do not modify behavior just to make tests pass. When an external dependency blocks testing, state "BLOCKED — external dependency unavailable" honestly and test everything possible around that boundary. Confidence: 0.7
- Wants findings classified by priority (P0 critical → P3 minor), with each issue backed by exact request, expected vs actual behavior, code path, root cause, recommended fix, and a proving test. Confidence: 0.6
- Prefers structured, comprehensive deliverables (executive summary, capability/inventory tables, failed tests, security findings, coverage counts, recommended fix order) over vague prose. Confidence: 0.5
- When given a detailed prompt or spec, wants it followed exactly and end-to-end without deviating from the prescribed structure. Confidence: 0.5
- After receiving a findings/audit report, expects every listed issue to actually be remediated rather than triaged down to only the critical items — and addressed one by one (priority-ordered, with the test suite re-run and verified along the way). Confidence: 0.55
- Wants explanations in plain, non-technical language ("simple terms that even my grandma would understand") — plain analogies over jargon when explaining judgment calls or design decisions. Confidence: 0.6
- Asks for explicit calibrated confidence ("how sure are you?") and expects honest uncertainty — claims broken into proven/measured vs unverified, instead of a flat "yes". Confidence: 0.55
- Wants features built out thoroughly and deeply ("build this out properly and deeply") — favors a complete, well-explored implementation over a minimal patch, especially for security-critical flows (identity, money, account creation). Confidence: 0.55
- Explicitly values "working on testing properly" as its own effort — willing to spend whole turns closing test-infrastructure gaps (e.g., testing serialization against a real backing store instead of in-memory fakes, fixing suites that don't compile, adding a CI/type-check gate for previously-unbuilt test tags) rather than pushing feature code forward. Confidence: 0.5
- Prefers consequential design/product decisions to be surfaced as targeted questions with concrete options and their tradeoffs, rather than the agent choosing silently — and engages with and answers those option sets. Confidence: 0.5
